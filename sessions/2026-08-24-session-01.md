Repository reset, initial theme build, and the page template system.

Covers theme versions **1.0.0** and **1.1.0**.

## Part 1 — Clean slate and the starter theme

### What was asked

- Empty the entire repository.
- Create a clean, standard WordPress starter theme.
- Push to `main` only. No extra branches.
- Do not add any tool or assistant to Contributors, and leave no trace of one in
  the repository. Push everything as the owner's own Git user.
- Write a `README.md` with initial content.
- A `style.css` header block was supplied verbatim, with the `Description` left
  to be written.
- Browser access would be granted later to install the theme on the owner's live
  WordPress dashboard.

### What was found

The repository held an unrelated Vite/React project — `components/`, `src/`,
`vite.config.ts`, `tsconfig*.json` — with `node_modules/` committed. 11,138
tracked files in total.

### What was done

The working tree was emptied and replaced with a 34-file WordPress theme:

- Full template hierarchy: `index`, `single`, `page`, `archive`, `search`,
  `404`, `header`, `footer`, `sidebar`, `comments`, `searchform`, plus five
  partials in `template-parts/content/`.
- `functions.php` loading four modules from `inc/`: setup, enqueue,
  template-tags, customizer.
- `style.css` carrying only the theme header; `main.css` holding the rules,
  built entirely on CSS custom properties.
- `rtl.css`, `theme.json`, `languages/moghadam.pot`, GPLv3 `LICENSE`,
  `.gitignore`, `.editorconfig`, `.gitattributes`, a placeholder
  `screenshot.png`.

### Corrections made during the build

**`Theme URL` → `Theme URI`.** The supplied header used `Theme URL:`, which
WordPress does not recognise; the theme link would never have appeared in the
dashboard. Corrected and flagged. → [D-002](../docs/02-decisions.md#d-002-theme-uri-not-theme-url)

**RTL stylesheet loading.** The build first used
`wp_style_add_data( 'moghadam-style', 'rtl', 'replace' )`, which makes WordPress
look for `style-rtl.css` — but `style.css` holds only the theme header, so the
replacement would have loaded an almost-empty file. Switched to an explicit
conditional enqueue of `rtl.css` guarded by `is_rtl()`.

**Customizer script dependency.** `customizer.js` uses jQuery; `jquery` was
added to its dependency array.

### Verification

PHP is not installed on the owner's machine, so `php -l` could not be run. All
21 PHP files were checked structurally instead — balanced braces, parentheses
and brackets, and matching PHP tags — and passed. This limitation was stated
plainly rather than implying the code had been executed.

### Result

Commit `8699015`, authored `Sayid Moghadam <i@moghadam.pro>`. No co-author
trailer, no tool attribution. A grep for assistant or generated-by markers
returned nothing.

## Part 3 — Planning the site theme

### What was asked

The theme is for the owner's personal introduction site, so it should be made
optional and configurable — carefully and by the book. Questions and proposals
were explicitly requested.

Stated requirements:

- Content is written in the standard WordPress editor. **The theme supplies
  style and structure only.**
- A set of page templates: Default, Canvas, Full Width, Theme, Home Page,
  Single Post, Archive Post, Single Portfolio, Archive Portfolio.
- Canvas loads purpose-written source — HTML, CSS, JS — outside the WordPress
  frame, with no influence from the theme's styling, **but keeping the meta and
  structure the site's SEO depends on**.
- A dedicated settings menu in the dashboard sidebar, with sections added over
  time. First section: **Variables** — colours, typography, and where each is
  used.
- Light and dark modes defined in those variables and adjustable in settings.
- Push at the end of every phase with a changelog and version, on both branches.
- A documentation branch recording all the chats here, the changes and
  corrections, and the rules and definitions.
- The two branches stay separate; `main` holds only the latest theme version.

### Questions asked, and the answers

**1. Where should the Portfolio custom post type be registered?**
Options offered: in the theme; in a companion plugin in the same repository; via
CPT UI or ACF.

> **Answer:** Drop Portfolio from this phase. A dedicated plugin will be written
> for it later.

Both portfolio templates were removed from the plan.
→ [D-005](../docs/02-decisions.md#d-005-portfolio-deferred-to-a-plugin)

**2. How should dark and light modes behave?**
Options offered: automatic with a toggle; automatic only; a fixed mode chosen in
settings; a settings default plus a toggle.

> **Answer:** Automatic with a toggle.

Follows `prefers-color-scheme`, visitor can override, choice persists in
`localStorage`. → [D-006](../docs/02-decisions.md#d-006-dark-and-light-modes--automatic-with-a-toggle)

**3. What is the "Theme" template meant to do?**
This was the one genuinely ambiguous item in the list. Options offered: a style
guide page; a full template with header and footer; a landing page introducing
the theme itself.

> **Answer:** A style guide page.

→ [D-007](../docs/02-decisions.md#d-007-the-theme-template-is-a-style-guide)

**4. What name and language for the documentation branch?**
Options offered: `docs` in Persian; `docs` in English; `docs` bilingual;
`documentation` in Persian.

> **Answer:** `docs`, in English.

→ [D-009](../docs/02-decisions.md#d-009-documentation-on-a-separate-orphan-branch)

### The agreed plan

| Phase | Version | Scope |
| --- | --- | --- |
| 1 | 1.1.0 | Template system, Canvas, layout classes, `docs` branch |
| 2 | 1.2.0 | Settings menu and Variables (light and dark token sets) |
| 3 | 1.3.0 | Dark/light runtime and editor style matching |
| 4 | 1.4.0 | Style guide wired to the real tokens |

## Part 4 — Phase 1 implementation (1.1.0)

### Added

- `page-templates/template-canvas.php` — bare document, no theme assets, full
  `wp_head()` and `wp_footer()`.
- `page-templates/template-full-width.php`
- `page-templates/template-home.php` — with two action hooks.
- `page-templates/template-styleguide.php` — the `Theme` template.
- `inc/layout.php` — `moghadam_main_class()`, `moghadam_get_layouts()`,
  `moghadam_has_sidebar()`.
- `inc/canvas.php` — Canvas behaviour and the
  `moghadam_canvas_dequeue_handles` filter.
- `inc/style-guide.php` — filterable token definitions.
- `CHANGELOG.md`.
- Sections 4a and 12 in `main.css` — layout variants and style guide styles.

### Changed

- Six existing templates now declare their layout through
  `moghadam_main_class()` instead of a hard-coded `class="site-main container"`.
- `sidebar.php` defers to `moghadam_has_sidebar()`, removing the need for a
  per-template guard.

### Where the Canvas line was drawn

Recorded in full in
[D-008](../docs/02-decisions.md#d-008-canvas-keeps-seo-drops-presentation). The
short version: the theme's stylesheets, scripts and `theme.json` global styles
are removed, along with the site chrome, `wpautop` and the admin bar. `wp_head()`
and `wp_footer()` are kept in full, so every SEO signal behaves as it does
elsewhere. Plugin assets are left alone.

### Notes on tooling

The POT generator initially matched only the `esc_*` translation wrappers, so
plain `__()` calls in the two new modules were missed. The extraction was
extended to cover `__()` and `_e()` with a lookbehind so it does not double-match
the escaping wrappers. String count went from 34 to 98.

The PHP structure checker reports one persistent false positive on
`inc/customizer.php`: it strips `#` comments before strings, so the two
`'#2563eb'` hex colour literals swallow the rest of their lines and the
parenthesis count comes out short by two. Verified by hand; the file is
balanced.

### Result

Commit `650949a`, tagged `v1.1.0`.
