Covers theme version **1.2.0**.

## Part 1 — Answers to the two open questions

Session 01 ended with two questions blocking phase 2.

### Question 1 — Variables vs. the Customizer accent control

> **Answer:** do your own proposal.

The proposal was that Variables becomes the single source of truth and the
Customizer accent control is removed. Implemented.
→ [D-011](../docs/02-decisions.md#d-011-variables-is-the-single-source-of-truth-for-design-tokens)

### Question 2 — Should `theme.json` be generated from the settings?

> **Answer:** what is your proposal? Does it not contradict your answer to the
> first question?

A fair challenge, and worth answering directly rather than just implementing.

**Proposal:** filter `theme.json` at runtime through `wp_theme_json_data_theme`.
The file stays in the repository as the default; the stored palette and layout
widths are overlaid when WordPress assembles the theme data.

**No contradiction — it is the same decision applied.** Question 1 was about
*where a value is set*, and the problem with the Customizer was that it made one
value settable from two screens. `theme.json` is not a second place to set a
value; it is a **consumer** of the one place. Variables is the source, and both
`main.css` and the block editor palette read from it. The failure being avoided
is precisely the one D-011 avoids: a hand-maintained `theme.json` drifting away
from the settings.

Physically rewriting the file on save was rejected — it breaks on read-only
installations and pollutes a version-controlled file with database state.
→ [D-012](../docs/02-decisions.md#d-012-themejson-is-filtered-at-runtime-not-rewritten)

**Constraint stated:** the filter needs WordPress 6.1. On 6.0 the static values
apply unchanged, which is graceful degradation rather than breakage, so the
theme's declared minimum was left at 6.0.

## Part 2 — PHP installed

Sessions 01 had no PHP available, so `php -l` could not be run and only a
structural check was possible.

`winget install PHP.PHP.8.3` failed with a 404: the manifest pointed at
8.3.32, but php.net had already moved to 8.3.33 and removes superseded builds.
Installed from the official Windows build instead:

- **Version:** PHP 8.3.33 (NTS, x64)
- **Location:** `%USERPROFILE%\tools\php`
- **PATH:** added to the *user* PATH, no elevation required
- **Removal:** delete the folder and the PATH entry

**First real lint of the whole theme: all 28 PHP files passed.** This also
retired the false positive the old structural checker reported on
`inc/customizer.php` — it stripped `#` comments before strings, so the two
`'#2563eb'` hex literals swallowed the rest of their lines.

## Part 3 — Phase 2 implementation (1.2.0)

### The schema

`inc/variables.php` holds one schema that the settings screen, the front-end
CSS and the block editor palette all read from. Adding a token means editing one
array; all three follow.

| Group | Per mode | Control | Tokens |
| --- | --- | --- | --- |
| Colors | Yes | colour picker | Accent, Text, Muted, Background, Surface, Border |
| Typography | No | text / size | Body, heading, mono fonts; base size; line height |
| Spacing and sizing | No | size | Five spacing steps, radius, content and container widths |

Every token carries a `usage` string describing where it applies, shown in the
settings table — this was an explicit requirement ("و جایگاه های استفاده").

The `bg` token key was renamed to `background` before anything was stored, so
the block editor palette slug reads sensibly.

### The settings screen

`inc/settings.php`. Top-level **Moghadam** menu at position 59, just under
Appearance. Built on the Settings API, with a tab registry
(`moghadam_settings_tabs`) so phase 3 and later sections plug in without
touching the rendering code. One option, `moghadam_settings`. Includes a
"Restore defaults" action behind a nonce and a capability check.

### Output

Three blocks, attached inline to `moghadam-main`:

```css
:root { /* light */ }

@media (prefers-color-scheme: dark) {
	:root:not([data-theme="light"]) { /* dark */ }
}

:root[data-theme="dark"] { /* dark */ }
```

The `:not([data-theme="light"])` guard is the detail that makes the phase 3
toggle work in both directions — without it, a visitor on a dark OS who chooses
light would still get dark, because the media query would keep matching.
→ [D-013](../docs/02-decisions.md#d-013-both-colour-sets-are-always-written)

`wp_add_inline_style` was chosen over echoing into `wp_head`: the cascade order
becomes explicit, there is no extra request, and Canvas already dequeues
`moghadam-main`, which correctly takes the variables with it.
→ [D-014](../docs/02-decisions.md#d-014-generated-css-is-attached-inline-to-the-main-stylesheet)

### Validation

Values end up inside a `<style>` block, so escaping on output is not sufficient
— they are validated on the way in. Colours must pass `sanitize_hex_color()`;
sizes must be a CSS length, a unitless number, or a `calc()`-family expression;
free text is stripped of tags, CSS comments and `{ } ; < > \` and rejected
outright if it contains `url(`, `expression(`, `javascript:`, `@import` or
`behavior:`. Commas and quotes survive, because font stacks need them.

Unknown groups and tokens are discarded rather than stored. A value that fails
validation falls back to its default rather than being stored empty, so the site
can never render with a missing token.
→ [D-015](../docs/02-decisions.md#d-015-stored-values-are-validated-not-merely-escaped)

### Verification

A standalone harness was written that loads the real `inc/variables.php` with
WordPress stubbed out, and asserts against defaults, merging, validation and
generated output — including injection attempts through every control type.

**40 assertions, all passing.** One assertion failed on the first run and it was
the test that was wrong, not the code: it expected each colour token twice, but
the correct output writes light once and dark twice, so three is right.

All 31 PHP files and all three JavaScript files lint clean.

### Fixes made during implementation

- An empty Customizer section was written first as a pointer to the settings
  screen. WordPress hides sections with no controls, so it would have been dead
  code. Removed rather than worked around.
- The per-mode rows had a `<label for>` pointing at an id that only existed on
  single-value rows. Per-mode rows now use `<strong>` for the row heading and
  `aria-label` on each of the two inputs.
- `moghadam_variables_schema()` and `moghadam_get_settings()` were called
  repeatedly per request; both are now memoized.
- The theme.json filter would fatal if the colours group were filtered away;
  guarded.
